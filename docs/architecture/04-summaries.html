04 · Summaries

Explaining repos

A repo name and a star count don't tell you what something does. So for every trending repo, Starling asks Google's Gemini to read the README and write one plain-language paragraph a non-expert can understand.

Only where it matters

Summaries are written only for the repos that actually make a trending list — a few hundred a day, not all 120,000. That's what keeps this step fast and essentially free.

The prompt is deliberately strict

The instructions given to Gemini are the interesting part. It's told to:

  • use only facts present in the README — invent nothing;
  • say plainly if the README doesn't make the purpose clear, rather than guess;
  • avoid jargon and marketing words ("powerful", "seamless");
  • write 2–4 sentences, present tense, and stop.

The result reads like a knowledgeable friend explaining the project, not a product page. For example, one real output described a repo as "a guide to free, ad-free resources for watching shows and movies… it automatically checks the validity of these resources daily."

Write once, reuse forever

Summarizing the same repo every night would be wasteful. So each summary is cached and tagged with the version of the README it was written from (a content fingerprint). On later runs, Starling only calls Gemini again if that README has actually changed.

Why it's basically free: a small, cheap model (gemini-2.5-flash-lite), only on trending repos, and cached after the first time. In testing, dozens of summaries cost a fraction of a cent and a re-run made zero API calls.
