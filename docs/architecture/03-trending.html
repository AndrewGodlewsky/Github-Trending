Finding what's trending

This is the heart of the product — deciding what counts as "trending." Starling ranks repos by how fast they're gaining stars, in percentage terms, with a small guardrail so it isn't fooled by noise.

The definition

For each repo, in each time window, Starling looks at two things:

  • Percentage growth — a repo going 500 → 650 (+30%) is more "trending" than one going 50,000 → 53,000 (+6%), even though the second gained more stars. Percentage surfaces the risers, not the giants.
  • A minimum absolute gain — but a repo can't sneak in on percentage alone. It also has to add a real number of stars, so a tiny wobble doesn't register as a trend.

Repos that clear both bars are ranked by percentage, and the top 50 in each window make the list.

Three windows

Day
today vs ~1 day ago
·
Week
today vs ~7 days ago
·
Month
today vs ~30 days ago

The clever part: tolerating gaps

What does "7 days ago" mean if the pipeline happened to miss a day that week? This is where DuckDB's ASOF join earns its place. Instead of demanding an exact date, Starling asks for "the most recent snapshot at or before the window's edge."

In plain terms: if last Tuesday's run was skipped, the week comparison just uses Monday's instead — automatically. A missed day makes the baseline a little older, not broken. Starling even notes the real elapsed days so a two-day catch-up isn't mistaken for a one-day spike.

A couple of edge cases it handles

  • Brand-new repos that just crossed 500 stars have no earlier snapshot to compare against, so they're held out of a window until there's a baseline — no fake "infinite growth."
  • Partial days (flagged in the runs logbook) are never used as a comparison point, so an incomplete crawl can't invent phantom drops.

An example from real data

On the day this was built, the top day-window riser was bojieli/ai-agent-book — up +1,071 stars (+45%) in 24 hours. The week list was led by repos more than tripling their stars. The month list surfaced repos that had gained tens of thousands. All computed from the same table with the same query, just different window sizes.

Tunable, not fixed. The exact thresholds live in one place (WINDOWS in trending.py). They start as sensible defaults and are meant to be nudged once you've watched a few days of real results — the code even reports the real distribution to guide you.
