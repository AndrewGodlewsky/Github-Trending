Running it daily

One module, orchestrate.py, is the conductor. It runs the six stages in order, once a day, unattended — and it's built to fail safely.

The nightly sequence

1 · ingest
crawl → today's snapshot
↓
2 · rank
compute the three windows
↓
3 · summarize
only new trending repos
↓
4 · assemble
write latest.json
↓
5 · publish
upload to Cloudflare — last, and only if all above succeeded

What makes it safe

Publish is last, and gated

The live site is only updated at the very end, after every earlier step worked. If the crawl fails, or Gemini has a bad night, the site simply keeps yesterday's data. Visitors never see a half-computed or broken page.

You hear about failures

If a run fails, Starling posts a message to your Discord channel (via a webhook) so you know without checking logs. A successful ingest is still recorded as complete even if a later step failed — the day's snapshot is valid, only the publish didn't happen.

It survives a sleeping laptop

The job is registered with Windows Task Scheduler to run once a day. If the machine was asleep or off at that time, it runs as soon as it can afterward — producing a slightly late snapshot rather than a missing day (which, as you saw, the trend math tolerates anyway).

Secrets

Your GitHub and Google keys, and the Discord webhook, live in a .env file that is never committed to git and never printed to logs. The code reads them at the moment of each call and nowhere else.

The runs logbook ties it together. It's what lets a crashed crawl resume where it stopped, what marks a day complete or partial, and what the trend math consults to decide which days to trust. One small table, doing quiet but essential work.

That's the whole system — six small stages, one local database, and one tiny file that reaches the web. Back to the overview →
