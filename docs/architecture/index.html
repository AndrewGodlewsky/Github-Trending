Architecture · Overview

How Starling works

Starling is a nightly batch job that runs on your PC. Once a day it takes a snapshot of every popular GitHub repository, works out which ones are gaining stars fastest, writes a plain-language summary of each, and publishes a small file that a website reads. That's the whole system.

Everything heavy — a database of ~120,000 repos and weeks of history — stays on your machine. Only a tiny result (a few hundred repos with their summaries, ~140 KB) ever goes to the internet. The public site is just static files reading that one result.

The daily loop

Every night, six stages run in order. Each hands its output to the next:

1 · Ingest
crawl GitHub → today's star counts
↓
2 · Store
save the snapshot in DuckDB
↓
3 · Rank
compute day / week / month risers
↓
4 · Summarize
Gemini explains each new riser
↓
5 · Assemble
write latest.json
↓
6 · Publish
upload the site to Cloudflare
The golden rule: publishing is the last step, and only happens if every earlier step succeeded. If anything breaks, the live site simply keeps yesterday's data and you get a Discord alert — a stale-but-correct site beats a fresh-but-broken one.

The stack at a glance

language
Python 3.14 (managed with uv)
database
DuckDB — a single local file, no server
data source
GitHub REST Search API + a seeded CSV history
summaries
Google Gemini (gemini-2.5-flash-lite)
website
plain HTML/CSS/JS — no build step
hosting
Cloudflare Pages (static)
schedule
Windows Task Scheduler, once a day
alerts
Discord webhook on failure
Why this shape? The design keeps the expensive, private part (the full database) on your machine and makes the public part as simple as possible — static files. That means no server to run, no database exposed to the internet, and near-zero hosting cost.
