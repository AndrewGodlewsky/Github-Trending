Getting the data

Starling needs one number for every popular repo, every day: its star count. Data arrives two ways — a live daily crawl of GitHub, and a one-time backfill of history you already had.

The live crawl (module: ingest.py)

Once a day, Starling asks GitHub's Search API for every repository with 500 or more stars. There's a catch that shapes the whole design:

  • The Search API returns at most 1,000 results per query.
  • It allows only about 30 requests per minute.
  • There are roughly 120,000 repos over the 500-star line.

So you can't just ask for "all repos ≥500★." Instead, Starling slices the range into star bands — stars:500..512, stars:513..528, and so on — each narrow enough to hold fewer than 1,000 repos, then pages through each band. It figures out where to draw each band automatically by probing the counts.

GitHub Search API
stars:500..N

A nice shortcut: each search result already includes the star count, so a single crawl produces a complete snapshot of all ~120k repos with zero extra per-repo calls.

Because of the rate limits, a full crawl takes about 2–3 hours — GitHub deliberately throttles heavy searching. That's fine for an unattended nightly job, and it's exactly why Starling runs on a schedule rather than on demand. If the crawl is interrupted, it can resume from the band it reached rather than starting over.

The history backfill (module: backfill.py)

Trends need history: "week over week" needs 7 days of data, "month over month" needs ~30. Starting from scratch would mean a blank first month. But you already had ~9 weeks of daily CSV snapshots sitting in a data/ folder — so those were loaded once, giving full trends from day one.

loaded
120,641 repos, one row per repo per day
span
2026-05-17 → 2026-07-18 (contiguous)
cleaning
de-duplicated rows, dropped one corrupted day, flagged two partial days

The live crawl then simply continues from where the history ends — today's snapshot lands after July 18, and every day after that.

Two sources, one shape. Both the crawl and the backfill write into the same snapshots table, so from that point on the rest of the system doesn't care where a given day came from.
