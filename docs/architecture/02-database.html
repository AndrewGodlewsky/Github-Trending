Where it lives

All the data sits in a single DuckDB file on your machine — github_trending.duckdb. No database server, no cloud, no setup. It's one file you could copy to a USB stick.

DuckDB is built for exactly this kind of work: lots of rows, and questions like "compare this to how it looked a week ago." It stores data by column, which makes those questions fast and keeps repeated values (like a star count that barely moves) tiny on disk.

Two design choices worth knowing

Every repo, every day (even if unchanged)

Starling stores a row for a repo every day, even when its star count didn't move. That sounds wasteful, but it's deliberate: it lets the system tell the difference between "stars held steady" and "we didn't run that day." If it only stored changes, a quiet repo and a missed day would look identical — and the trend math would break. Columnar storage makes those repeated rows almost free.

The runs logbook

A nightly crawl can be interrupted, or a day can be partial. The runs table records the outcome of each day (complete, partial, failed, absent). The trend calculations only trust complete days, so a bad night never poisons the results.

Why DuckDB specifically? It has a feature called an ASOF join — a way to ask "what was this repo's star count on the most recent day at or before a week ago?" That one feature makes the trend math both simple and robust to missing days. More on that next.
